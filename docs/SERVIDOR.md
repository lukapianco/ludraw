# Rodando o servidor (Modo Servidor)

O servidor fica em `server/` (Node.js + Fastify + PostgreSQL via Drizzle). Ele guarda os boards, aplica as mesmas permissões do app (`can()`), faz login com e-mail/senha (argon2) ou com o login da empresa (OIDC genérico) e protege os links públicos de verdade.

```bash
docker compose -f server/docker-compose.dev.yml up -d   # PostgreSQL de desenvolvimento
cp server/.env.example server/.env                      # ajuste DATABASE_URL e o que mais precisar
npm --prefix server install
npm run server:dev                                      # http://localhost:3001 — mostra o token de configuração UMA vez no log
npm run dev                                             # em outro terminal: http://localhost:5173 (o /api vai para o servidor)
```

**Detecção automática:** ao abrir, o app pergunta `/api/v1/info` na própria origem (até ~1,5 s). Se um servidor LuDraw responder, ele entra direto no **Modo Servidor** (travado nesse endereço): com o servidor ainda sem configuração vai para o **primeiro acesso** (`#/setup`), senão para a entrada com o nome da organização e o SSO. Sem servidor, fica no **Modo Local** com o botão **Conectar a um servidor Homelab**. O Modo Local, quando há servidor, vem **bloqueado** por padrão: libere com `LUDRAW_ALLOW_LOCAL_MODE=true` ou em **Admin → Políticas e domínios → Permitir modo local neste servidor**. Frontend publicado separado do backend: um `config.json` ao lado do `index.html` (`{ "serverUrl": "https://draw.example.com" }`) ou `VITE_DEFAULT_SERVER_URL` no build. Em desenvolvimento, `?local=1` na URL (ou `LUDRAW_FORCE_LOCAL=1` no `npm run dev`) força o Modo Local, e `LUDRAW_API_PROXY` muda para onde o `/api` do Vite aponta. Na imagem Docker o app vem do próprio servidor, na mesma origem: não há `config.json` nem proxy para configurar.

Conclua o **primeiro acesso** com o token do log (perdeu? `npm --prefix server run setup:token`; no Docker, `docker compose exec app ludraw setup:token`). Também dá para criar a organização e o administrador pelas variáveis `LUDRAW_ORG_NAME`, `LUDRAW_ADMIN_EMAIL` e `LUDRAW_ADMIN_PASSWORD` (ou `_FILE`, o caminho certo no Docker): rodam uma única vez, só com o banco vazio, e o administrador troca a senha no primeiro login. Recuperação: `npm --prefix server run admin:reset-password -- --email ana@empresa.com` e `admin:create`; no Docker, `docker compose exec app ludraw admin:reset-password --email ana@empresa.com --generate` (a senha nova aparece uma vez) ou `docker compose exec -T app ludraw admin:create --email bia@empresa.com --password-stdin < senha.txt`. A senha nunca vai como argumento. Todas as variáveis estão comentadas em [`server/.env.example`](../server/.env.example); as do Docker, no [DOCKER.md](DOCKER.md#configuração).

> 🔐 **Segredo das sessões:** defina `LUDRAW_JWT_SECRET` no ambiente (ex.: `openssl rand -base64 48`) — é o mais seguro, porque fica fora do banco. Sem ele, o servidor gera uma chave e a guarda no próprio banco: conveniente, mas quem lê o banco consegue forjar sessões. **No Docker isso já vem feito:** o `node scripts/docker-secrets.mjs` cria o arquivo `jwt_secret`, que o app lê por `LUDRAW_JWT_SECRET_FILE`. Valores de exemplo ou fracos são recusados no boot, e em produção a chave precisa ter pelo menos 32 caracteres.
>
**Papéis do banco (Chat 09):** em produção o app não roda como dono das tabelas. São três papéis: `ludraw_owner` (dono, sem login), `ludraw_migrator` (roda as migrações) e `ludraw_app` (só lê e grava dados, sem `CREATE`; cada consulta tem até 15 s e uma transação parada cai em 30 s). Com os papéis, `DATABASE_URL` aponta para `ludraw_app` e `LUDRAW_MIGRATE_DATABASE_URL` para `ludraw_migrator`; `npm --prefix server run db:roles -- --database ludraw` imprime o SQL. Fora de produção o servidor migra sozinho ao subir; em produção, não (`LUDRAW_MIGRATE_ON_BOOT`), e com migração pendente ele **não sobe**. O compose do Docker já cria os papéis e roda a migração num serviço próprio antes do app ([DOCKER.md](DOCKER.md#papéis-do-banco)). Em desenvolvimento, o banco do `docker-compose.dev.yml` com um usuário só continua funcionando.

**Edição ao vivo (Chat 08):** com o servidor, várias pessoas editam o mesmo board ao mesmo tempo (WebSocket em `/api/v1/collab`, na mesma porta da API). Atrás de proxy reverso, libere o *upgrade* de WebSocket nesse caminho. Variáveis: `LUDRAW_COLLAB` (padrão ligado), `LUDRAW_COLLAB_MAX_PAYLOAD_MB` (padrão 24), `LUDRAW_COLLAB_STORE_DEBOUNCE_MS` (padrão 2000) `LUDRAW_COLLAB_MAX_CONNECTIONS_PER_USER` (padrão 12) e `LUDRAW_COLLAB_SELECTION_IDLE_SECONDS` (padrão 300: tempo sem atividade até o servidor soltar o objeto que a pessoa selecionou). As salas vivem na memória do processo, então o tempo real funciona com **uma instância** do servidor; para rodar várias, desligue-o (`LUDRAW_COLLAB=false`: os boards passam a ser salvos e recarregados). Teste com dois navegadores: `npm run test:collab:browser`.

**Várias instâncias com Redis/Valkey (Chat 09, opcional):** com uma instância, não precisa de nada. Com várias atrás de um balanceador, aponte `LUDRAW_REDIS_URL` (ou `_FILE`; `redis://` ou `rediss://`) para um Valkey (ou Redis até 7.2 — o 7.4 em diante tem licença que o projeto não aceita): os limites de tentativa, o teto de pedidos por IP e o aviso "o painel de e-mail mudou" passam a valer para todas. Configurado e fora do ar quando o servidor sobe, ele **não sobe**; se cair com o servidor rodando, login, e-mail e links com token respondem 503 até ele voltar, e o resto continua. No Docker é o perfil `redis` do compose ([DOCKER.md](DOCKER.md#redisvalkey-opcional-para-mais-de-uma-instância)).

**Imagens no servidor (Chat 08.2):** no Modo Servidor as imagens dos boards ficam numa pasta do servidor (`LUDRAW_ASSETS_DIR`, padrão `server/data/assets`; no Docker, o volume `assets`, em `/data/assets`), não dentro do board: o board guarda só uma referência e cada imagem só é entregue a quem pode ver um board que a usa. **Backup = banco + essa pasta** — no Docker, `node scripts/docker-backup.mjs backup` copia os dois ([BACKUP.md](BACKUP.md)). Imagens sem nenhum board são apagadas pela manutenção 24 h depois. O servidor não sobe se não conseguir gravar nessa pasta. O Modo Local continua com as imagens dentro do board.

**E-mail (Chat 08.5, opcional):** sem e-mail o servidor funciona igual (convite por link/código e senha redefinida por um administrador). Com e-mail entram **Esqueci minha senha**, a **confirmação de e-mail**, **convites por e-mail**, o **link de convite geral**, os **pedidos de acesso** e, se a política for ligada, o **cadastro com o e-mail da organização**. Duas formas de ligar, que podem ser combinadas numa instalação `single_org` (no `multi_org` o e-mail é do servidor inteiro e só vale a forma 2 — o painel não aparece para nenhuma organização):

1. **Pelo painel:** **Administração → Políticas e domínios → Envio de e-mail** (servidor SMTP, porta, usuário, senha e remetente), sem reiniciar, com o botão **Enviar e-mail de teste**. Para o painel guardar a senha, defina `LUDRAW_JWT_SECRET` no ambiente (a senha é cifrada com uma chave derivada dele).
2. **Por variáveis** no `server/.env` (no Docker, em `deploy/ludraw.env`) — elas vencem o painel campo a campo:

```bash
LUDRAW_SMTP_HOST=smtp.example.com
LUDRAW_SMTP_PORT=587                     # 465 = TLS desde a conexão; nas outras portas o servidor exige STARTTLS
LUDRAW_SMTP_USER=ludraw@example.com
LUDRAW_SMTP_PASSWORD_FILE=/run/secrets/smtp_password   # ou LUDRAW_SMTP_PASSWORD (no Docker, use o arquivo: DOCKER.md, "Segredos extras")
LUDRAW_SMTP_FROM="LuDraw <no-reply@example.com>"
LUDRAW_APP_URL=https://draw.example.com  # endereço usado nos links dos e-mails (padrão: LUDRAW_PUBLIC_URL)
```

Os links dos e-mails saem **só** de `LUDRAW_APP_URL` (nunca do cabeçalho `Host`); com e-mail ligado e sem ela (nem `LUDRAW_PUBLIC_URL`) o servidor não sobe. Limites por hora: `LUDRAW_MAIL_MAX_PER_ADDRESS_HOUR` (5), `LUDRAW_MAIL_MAX_PER_IP_HOUR` (20), `LUDRAW_MAIL_MAX_PER_USER_HOUR` (60, teto 300) e `LUDRAW_MAIL_MAX_PER_HOUR` (servidor inteiro, 300, teto 2000 — com a conta pessoal de um provedor grande, use 20 e uma "senha de app"); cadastro pelo domínio: `LUDRAW_DOMAIN_SIGNUP_MAX_PER_DAY` (50 contas por domínio a cada 24 h). Para testar sem SMTP, `LUDRAW_MAIL_OUTBOX_DIR=./data/outbox` grava cada mensagem como `.eml` + `.txt` (copie os links do `.txt`; com o Vite, `LUDRAW_APP_URL=http://localhost:5173`) — recusada em produção. Tudo comentado em [`server/.env.example`](../server/.env.example).

**Segurança do navegador (Chat 09):** o servidor (e o Vite, em desenvolvimento) envia a política de segurança do app (CSP) e os cabeçalhos de proteção, montados num lugar só (`src/utils/securityHeaders.ts`). Duas variáveis ajustam a política: `LUDRAW_FRAME_ANCESTORS` (sites que podem incorporar boards; padrão: só a própria origem) e `LUDRAW_CSP_CONNECT_SRC` (hosts extras para extensões com a permissão "rede" que você aprovou; padrão: nenhum). Com a CSP, o navegador não busca imagens de outros sites: no Modo Servidor, **"Baixar para o board"** é feito pelo próprio servidor, que recusa endereços internos da rede.

**Tela "Sistema visual" (Chat 09):** o guia de quem contribui com o LuDraw (`#/design-system`) aparece por padrão ao rodar do código. `LUDRAW_ENABLE_DESIGN_SYSTEM=false` o esconde — nenhum link, menu ou busca leva a ele e o endereço abre a tela inicial; a imagem Docker já vem assim. Sem servidor (Modo Local puro), ele continua disponível.

> 🕵️ **Privacidade (IPs):** o Audit Log guarda o IP de logins e ações sensíveis para investigação; depois de `LUDRAW_AUDIT_IP_RETENTION_DAYS` (padrão 90 dias) o IP é apagado e a entrada continua. Atrás de proxy reverso, ligue `LUDRAW_TRUST_PROXY` para registrar o IP certo. (Orientação de engenharia, não parecer jurídico.)
